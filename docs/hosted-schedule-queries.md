# Hosted schedules, workouts and booking views

[Issue #75](https://github.com/rudeayelo/aimharder-mcp/issues/75) extends the authenticated HTTP MCP surface with the existing `get_class_sessions`, `get_published_workouts`, `get_upcoming_bookings` and `get_booking_history` queries. Both `admin` and `user` have these queries without feature switches. This is one implementation slice of [the full hosted specification](https://github.com/rudeayelo/aimharder-mcp/issues/69), not a query-only replacement for the agreed product.

## Use and interpretation

Connect an invited, verified portal account, configure its [AimHarder connection](hosted-aimharder-connection.md), then authorize a trusted MCP client through the [client authorization flow](hosted-mcp-authorization.md). Tool inputs and successful results retain the [local query contract](tools.md): explicit gym-local dates, optional accessible `gymId`, and the reported gym zone/provenance. Credentials, portal subjects, upstream account IDs, publisher IDs and arbitrary URLs are not tool arguments. Relative-date questions must resolve dates using the selected gym's reported zone, checking any assumed zone with the participant.

- `get_class_sessions` accepts an inclusive date interval and optional exact class/time filters. It has no 31-date activity limit. Every daily schedule must succeed; a later failure is an error, not a complete or empty schedule. Missing occupancy/capacity remains null and actual zero remains zero. Occupancy is neither attendance nor final booking eligibility. Dates and wall times do not imply UTC instants at DST boundaries.
- `get_published_workouts` retains all applicable alternatives, labeled difficulty variants, original prescriptions, verified units and provenance. Applicability follows intended `recordDate` and source class, not publication time. Matching alternatives remain ambiguous; no unique workout/session link is invented. Coverage remains the incomplete upstream feed view. Available instructions can coexist with unsupported alternatives; absent feed content does not prove the date's workout is unpublished.
- Eligible current/future `%RM` prescriptions retain exact-ID own-account calculated loads, latest dated 1RM, precise arithmetic and original male/female alternatives. The entire workout read, including its bounded personal RM enrichment, runs inside one account operation. Ordinary personal-read failure preserves instructions with unavailable reasons; identity/access/authentication failure remains fatal. Past workouts do not receive present-day calculated loads.
- `get_upcoming_bookings` distinguishes booked, waitlisted and unknown states without inventing session IDs. Complete retrieval is scoped only to `upstream-upcoming-view`, with no verified future horizon. Absence cannot establish no booking on an arbitrary date. `get_booking_history` preserves partial recovery, source flags, late-cancellation precedence and unverified attendance; even complete retrieval is limited available history, never lifetime completeness.

Clients can compose context, schedules, workouts and upcoming bookings for “tomorrow's WOD and my booking.” Keep available instructions if the independent booking lookup fails, mark booking status unconfirmed, and retain publication ambiguity. No new combined server tool is introduced.

## Account boundary

The resource verifies current OAuth grant/admission before registering tools. Only its verified subject selects the private account object. Strict shared query schemas validate inputs before upstream access, and the object validates the same queries before using its owned client. A whole client query runs in the existing serialized account queue, including membership checks and bounded session recovery. The private success envelope wraps the unchanged result rather than merging it with an internal status field: public workout `status` values retain their own meaning. No session is shared between participants and no sporting-history replica is persisted.

This extends the accepted [encrypted account boundary](adr/2026-10-19-encrypted-aimharder-account-boundary.md) and preserves the [schedule](adr/2026-09-22-class-schedules-and-confirmed-time-zones.md), [zone](adr/2026-09-24-default-gym-time-zone.md), [workout](adr/2026-09-22-published-workout-applicability.md), [upcoming](adr/2026-09-22-upcoming-bookings-and-view-coverage.md), [history](adr/2026-09-22-booking-history-state-and-coverage.md) and [RM](adr/2026-09-27-personal-exercise-rms-and-calculated-loads.md) decisions. No new upstream capability or local stdio behavior is added.

## Validation boundary

Automated validation uses an actual SDK v2 HTTP client, maintained OAuth authorization, real workerd/D1/SQLite Durable Objects and the real AimHarder client, with synthetic external HTTP only. It does not establish actual ChatGPT/Hermes acceptance, new target-runtime query/source comparison, runtime cost, sporting writes or full action/lifecycle coordination. Those remain later tickets, including [#77](https://github.com/rudeayelo/aimharder-mcp/issues/77) and [#84](https://github.com/rudeayelo/aimharder-mcp/issues/84). No provider deployment or real upstream request is performed by this slice.

The isolated local package check also passed (31 files, 18 tools, empty stderr). Shared local source is unchanged; its historical full 471-test suite was not rerun for this hosted-only extension.
