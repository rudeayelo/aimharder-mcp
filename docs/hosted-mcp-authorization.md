## Boundary and behavior

The production Worker configuration must include `global_fetch_strictly_public` alongside `nodejs_compat`. The maintained JWT verifier fetches the configured canonical `/api/auth/jwks`; [Cloudflare's flag contract](https://developers.cloudflare.com/workers/configuration/compatibility-flags/#global-fetch-strictly-public) routes an own-zone global `fetch()` through the public front door, permitting it to re-enter the same custom-domain Worker. Without the flag, that fetch can target the zone origin while an ordinary external JWKS request succeeds. Retain canonical issuer/audience/key verification, current-grant checks and exact resource policy; this routing setting does not supply authentication or bypass it. Local tests with a same-origin outbound adapter do not establish the deployed front-door path.

| Public boundary | Behavior |
| --- | --- |
| `POST /mcp` without usable authorization | Maintained 401 challenge advertises protected resource discovery. Current-grant failures also return 401 with discovery. |
| `GET /.well-known/oauth-protected-resource/mcp` | Canonical MCP resource, authorization server and `mcp:access` resource scope. |
| `GET /.well-known/oauth-authorization-server/api/auth` | Maintained issuer, authorization/token endpoints, S256 and refresh support. No registration endpoint or CIMD capability is advertised. |
| `/api/auth/oauth2/authorize`, `/consent`, `/portal/oauth/consent` | Verified active portal session, explicit browser consent and the maintained signed OAuth query. OAuth login continuation returns only to the fixed local authorization endpoint. |
| `POST /api/auth/oauth2/token` | Maintained code/PKCE/resource checks and rotating refresh. Issuance also checks current admission and retains a durable original-grant identity. |
| `GET /connections`, `GET /api/portal/connections` | The signed-in active participant's authorized clients, without credentials or tokens. |
| `POST /portal/connections/{clientId}/revoke`, API equivalent | Same-origin authenticated revocation for that participant and client only. Atomically revoke grant records, remove its refresh/access rows and consent, and increment the client-revocation generation to invalidate pending code issuers. |
| `GET /connect-clients` | Participant instructions and the configured environment's endpoint. |

The maintained resource seeder merges only the configured environment's MCP resource policy to `mcp:access offline_access`, including an existing feasibility resource row. It does not replace unrelated resource policies. The consent page permits the redirect chain to only the origin of its exact registered callback: HTTPS ChatGPT or a fixed HTTP loopback callback. Other pages retain their own scoped policy; Google authorization is not allowed by MCP consent. The backend still validates the full callback URI and signed query. HTTP tests assert these CSP headers and rejection of a changed callback; native Chrome/ChatGPT/Hermes consent handoff remains #84 acceptance. The library verifies signature, issuer, audience, expiry and required scopes before application policy. Every MCP invocation also checks the signed portal subject, matching client and original grant against current D1 admission, email verification, client enablement and grant revocation. A token cannot select another portal account through tool arguments. Refresh retains the original authorization identity, so a stale refresh racing revocation cannot restore access. New authorization uses a new grant; old JWTs remain denied. Before maintained consent processing, the service snapshots this participant’s persisted client-revocation generations once for the entire HTTP request, including internal provider continuation. Codes and grants retain the selected generation; atomic insertion and every protected request require equality with current D1 state. Every new authorization asks for explicit maintained consent, including reconnecting a previously consented client; ordinary refresh remains automatic. A stale consent write therefore cannot silently reconnect a later authorization. Native verification timestamps are not used for revocation ordering. Connected-client API/HTML lists require both maintained consent and a current, unrevoked application grant for this participant/client and generation, with the client enabled. Pending unexchanged approvals are not listed until a usable grant is minted. A delayed stale consent row therefore cannot reappear as a connected client. Consent, OAuth tokens and portal login are separate state.

Better Auth's default access-token lifetime is one hour and refresh lifetime is 30 days. Its MCP refresh overlap is 30 seconds: a repeated refresh can return the previous rotation response during that window. The portal revocation ledger is independent of that overlap and immediately denies an already signed access token. Use the portal's **Connected MCP clients** control for immediate complete client revocation; deleting a client's local cached tokens or a provider consent record alone is not that operation.

`mcp:access` authorizes access to enabled service capabilities; it is not action-specific confirmation. This replaces the earlier feasibility-only `mcp:read` label before real client onboarding, so later confirmed booking/activity tools are never silently authorized under a read-only scope. Role checks, exact action previews, separate confirmation and read-back remain mandatory when those tools are implemented. Before the later vault/coordination/tool slices, only `get_account_context` is exposed. The deployed resolver has no upstream credentials and returns a safe not-connected tool result. Booking/activity write routes are absent from this slice. The local stdio package retains its independent SDK v1 and all existing tools.
