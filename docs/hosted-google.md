# Google sign-in and explicit portal account linking

Local implementation for [ticket #72](https://github.com/rudeayelo/aimharder-mcp/issues/72), under [specification #69](https://github.com/rudeayelo/aimharder-mcp/issues/69). The password/Resend journeys in [admission](hosted-admission.md) remain accepted. This document records synthetic Google evidence and the concrete operator/owner acceptance procedure; the exact provider origin/callback update is separately observed below, while secret injection and actual login/linking remain pending. See the [decision](adr/2026-10-18-google-sign-in-and-explicit-linking.md).

## Participant journeys

An invited participant can choose **Accept with Google** on the invitation page instead of creating a password. Google must report the exact invited email, lowercased without alias expansion, with `email_verified` equal to boolean `true`. The current invitation is rechecked and claimed atomically before issuing a portal session. Wrong-email, unverified, expired and revoked claims cannot join. Expiry or revocation after leaving the portal for Google still prevents admission. A returning admitted Google subject can sign in without replaying its accepted invitation. A changed provider email does not silently rebind the portal email.

If a password account already exists for that email, **Continue with Google** fails until the participant explicitly links the method. Matching email strings never merge accounts. Sign in using the existing method, open **Account access**, and choose **Link Google to this account**. Complete Google authentication using the same verified email. Both starting and completing the link require the same currently admitted portal session, created within the previous five minutes. Signing out, switching accounts or revoking the session while Google is open invalidates linking; sign in again and restart. The provider subject cannot be assigned to a different existing identity. Linking preserves the portal ID and profile; provider profile updates are disabled. Later AimHarder settings and grants remain keyed to that stable portal ID rather than to a provider method.

A Google-created account can explicitly add a portal password through **Account access**. Sign in with Google again and submit **Add portal password** within five minutes. The current verified active Google-only session proves account control; the maintained server-only password setter owns password policy and native hashing. Existing passwords cannot be overwritten through this route, including concurrent submissions. Subsequent Google and password login use the same identity. Password recovery becomes eligible only after adding that password; recovery remains unavailable for Google-only identities and retains its generic responses. Password recovery preserves the ID and revokes existing sessions as before.

The sign-in page preserves a pending MCP authorization query through Google and returns only to the fixed maintained authorization endpoint. That endpoint still validates the signed request, registered client and redirect; this is not a general return-URL facility. Google login is distinct from approving an MCP client.

## HTTP contract

| Route | Behavior |
| --- | --- |
| `POST /api/auth/sign-in/social` | Maintained redirect-only Google sign-in; invitation capability in `x-portal-invitation` for new admission; identity scopes fixed |
| `POST /api/auth/link-social` | Maintained explicit linking, admitted session younger than five minutes; callback rechecks the original session and verified same email |
| `GET /api/auth/callback/google` | Maintained state, PKCE/code exchange and provider profile; application admission/link gates before session/link mutation |
| `POST /portal/google` | Same-origin browser adapter; optional invitation and maintained MCP authorization continuation |
| `POST /portal/link-google` | Same-origin explicit browser link initiation |
| `GET /account` | Current participant's linked-method status and explicit addition forms; no credentials or provider tokens |
| `POST /api/portal/password` | Same-origin JSON `{ "newPassword": "..." }`, fresh admitted Google-only session; 200 added, 401 anonymous, 403 stale/ineligible, 409 existing password |
| `POST /portal/add-password` | Equivalent same-origin browser form using maintained server-only password setter |
| `GET /google-result` | Fixed safe failure guidance, without echoing provider errors or supplied query data |

Native ID-token sign-in, additional provider scopes and arbitrary authorization parameters are rejected. OAuth state carries invitation and original linking-session information under Better Auth's server-controlled `serverContext`, not caller-controlled `additionalData`. Google access/refresh tokens use the maintained encrypted-token setting; no new provider-token display endpoint is introduced. This does not implement the separate AimHarder vault/key rotation requirements.

## Verification and limits

On Node 24.14.0, eight new workerd/D1 HTTP journeys exercise the production portal/auth implementation with only the external Google token endpoint and Resend email API substituted. They cover verified admission/returning identity; uninvited/wrong-email/unverified/revoked/expired claims; implicit merge denial and explicit linking; revoked/swapped/stale linking sessions; Google-first password addition, recovery and stable ID/profile; concurrent password addition; changed provider email and unsupported token/scope requests; HTML controls and MCP authorization continuation. The synthetic token response is not proof of Google's live issuer, client, consent or callback behavior. Unexpected external requests fail the harness. Existing seventeen hosted scenarios remain green: twenty-five total, with hosted typecheck and production build passing. The local stdio source, lockfile and public API are unchanged; this slice adds no AimHarder API contract observation or real upstream request.

The operator separately observed the provider origin/callback update below. Testing admission, runtime secret injection, Google login and explicit linking still require their own operator/owner evidence. This local evidence alone does not close #72, validate an actual Google-first password addition, or establish ChatGPT/Hermes interoperability, deployed CPU/load/cost, AimHarder custody or the remaining hosted lifecycle.
