# Hosted own-activity publication

Issue [#79](https://github.com/rudeayelo/aimharder-mcp/issues/79) exposes `prepare_activity_publication` and `execute_activity_publication` through the protected hosted MCP endpoint. They run the existing real API client inside the participant-owned account queue. The [role decision](adr/2026-10-19-hosted-activity-role-access.md) and [action coordination](hosted-booking-creation.md) apply. This is synthetic implementation evidence, not activation or authorization of a real publication.

## Role access and participant journey

The administrator opens **Activity access by role** from the portal home page. Publication and deletion are independent role policies: initially enabled for `admin`, disabled for `user`, with no individual overrides. This ticket adds publication controls; deletion controls are delivered separately by #80. The administrator can disable publication for their own role without losing access to manage policies. Other query and booking tools have no switches.

Connect your own AimHarder account, configure a confirmed gym zone and authorize an MCP client. Select a verified source from `get_published_workouts`. Preparation retains the existing [source, variant, historical load, structured result, duplicate and audience rules](tools.md#prepare_activity_publication). A draft cannot execute. Show the full ready preview and obtain one separate account-holder confirmation of that exact publication before execution. Neither an administrator role nor `confirmed: true` independently establishes human consent.

Permission is checked from the current active verified participant's role before and after preparation and at execution. A role disabled during source reads receives no usable preview/reference. The final pre-fetch authorization checks the current role policy, grant/generation/client, admission and exact connection revision in the same D1 snapshot. Cached tools, previously issued references and setting changes during preflight cannot bypass it. A successful final guard admits that one external request; a later policy change cannot unsend it. Wrong/foreign/expired/repeated references cannot send another POST.

## Dispatch, recovery and limits

The locally implemented [residency amendment](adr/2026-10-21-bounded-preparation-residency.md) coalesces actor holds for unused publication preparations through their original two-minute expiry and releases them on consumption/discard. Permission remains memory-only, one-use and subject to current policy; restart still requires fresh preparation and confirmation. Deployment and a native-positive check remain separate.

The existing real client rechecks source/Copy mapping, selected date/variant/results/actual loads and account audience before dispatch. Exactly one POST can be attempted from a consumed reference. Fresh own-calendar/detail read-back preserves accepted/rejected/uncertain outcomes and only verifies original prescription provenance after a fresh matching source. No activity history is mirrored and no applied audience or RM side effect is inferred.

The existing ten-minute encrypted action journal retains bounded original intent: verified identity/membership, gym ID/zone and gym-name digest, source-summary digest, original-source-intent digest, intended activity date, original strict query, original audience, mapped-form digest and bounded response interpretation. It stores no source prescriptions/notes, historical RM suggestions, raw Copy payload, raw response, credentials or executable preparation. This keeps supported large source notes out of the journal while preserving them in the complete live preview, submitted content and own-entry comparison. The protected original query fits the shared 128 KiB UTF-8 facts bound; encryption and decryption enforce the same bound. Existing small encrypted booking envelopes remain readable.

A restart loses unused preparation. For possibly sent activity, recovery re-fetches the same original source and reconstructs comparison facts from the original query and audience, verifies the source summary, original intent and submitted-form digests, then checks the accepted ID in fresh original own calendar/detail. The original-intent digest covers normalized original prescriptions and the allowlisted mapped Copy form before achieved load or block-result overrides. This prevents achieved values from masking a changed source prescription. Derived RM displays are excluded, so their refresh does not alter source equivalence. Historical suggestion displays are not retained or recalculated. Missing/changed source does not skip available own read-back: inspect only the original accepted target, then report explicit `ACTION_OUTCOME_UNCERTAIN` when the original comparison/provenance cannot honestly be reconstructed. Without an accepted response ID, recovery remains uncertain rather than selecting a similar entry. A different supplied gym is refused before recovery reads. Missing original connection/revision/identity never causes a replacement-account query or restored old credentials.

Failure to save post-send facts still attempts own read-back and reports its honest result with a recovery limitation. Terminal-phase persistence failure cannot hide an already reconciled result. The prior durable fence prevents replay in both cases. Current role permission is still required for recovery. Journal expiry removes recovery details, not evidence that a possible upstream write never happened.

## Activation and validation

Apply migrations `0006-action-journal.sql` and `0007-activity-role-policy.sql` once before deploying a bundle containing this feature. Do not replay the isolated environment's historical manual migrations. The shared rotation command inventories and rewraps activity records through the existing journal contract; this ticket creates no additional maintenance endpoint or secret.

Eighteen added public portal/OAuth/SDK HTTP journeys exercise real workerd, D1, SQLite account objects and shared API client. Synthetic external responses cover administrator success, blocked user/disabled role, no individual exceptions, strict confirmation, concurrent/repeated and foreign references, changed audience/source, final role-change races, restart loss/read-only recovery, wrong recovery gym, denial/lost response/conflicting ownership/incomplete reads, journal faults, expiry, maximum-length escaped-comment recovery and large-source recovery through actual combined offline rotation/new-key-only restart, activity-specific reference errors and a policy change during held preparation, source changes masked by achieved loads/block results, and live provenance after a masked source change. Local source/result/variant/load rules retain the broader stdio regression coverage. Real publication, provider activation, actual ChatGPT/Hermes UI behavior, applied audience, broader upstream formats, costs and later lifecycle/restore acceptance remain separate and unobserved here. Every real publication still needs a new exact confirmation and fresh own read-back.
