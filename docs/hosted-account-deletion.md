# Hosted account deletion and controlled restore

[Issue #83](https://github.com/rudeayelo/aimharder-mcp/issues/83) implements owner deletion and a trusted restoration mechanism. The [decision](adr/2026-10-19-independent-deletion-and-controlled-restoration.md) specifies the authority, ordering and conditional retention argument. Application tests are synthetic. Actual provider backend/retention, native restore and key-recovery evidence must be recorded separately before acceptance; this document does not claim those gates passed.

## Participant behavior

Open **Account access → Delete portal account**, read the consequences, tick the explicit confirmation and submit. Browser `POST /portal/account/delete` and JSON `POST /api/portal/account/delete` share the same current-session, same-origin and strict `{ "confirmed": true }` checks. The JSON success is 204. Removal includes Google/password methods, sessions, MCP grants/tokens/consents, connection ciphertext, journal/preparations and associated invitation/admission records. It never cancels an upstream booking or deletes AimHarder activity.

Independent tombstones deny new use before app cleanup. A cleanup interruption returns 503 with access already blocked and operator cleanup pending. A held preflight loses final admission; a possible send still performs original-account read-back without replay, then queued memory erasure completes. The service never restores deleted persisted credentials to reconcile. Other established participants remain connected. Generic maintained pending verification/OAuth/reset state is conservatively invalidated because opaque encrypted state cannot reliably be attributed; an unfinished authentication transaction may need restarting.

## Bindings and activation

The new bundle requires **both** `AUTH_DB` and independent `RECOVERY_DB`, plus a pinned opaque `RECOVERY_AUTHORITY_ID`. Missing authority/schema/head fails closed even for authentication/mail/MCP routes. Keep the existing auth/mail/Google/vault bindings and private SQLite account namespace. Apply application migration `0009-account-deletion.sql` after `0008` exactly once; do not replay this test environment's initial migrations or assume a Wrangler ledger exists. Independently apply `hosted/recovery-migrations/0001-independent-authority.sql` only to the new recovery database. Its schema is also exported as `recoverySchema` for reviewed operator tooling.

Bootstrap a fresh pinned head under operator control, initially closed, with a random checkpoint and epoch zero. Verify exact database/binding identity, schema, authority ID and absence of earlier authority history before opening a genuinely new installation. Activation over an existing service needs a maintenance stop/drain of its previous unleased bundle; merely adding the new binding cannot fence old code already running. Do not initialize an empty head as recovery from a lost or rolled-back authority. Never restore or replace `RECOVERY_DB` along with application data. Keep its latest authenticated checkpoint independently discoverable through the trusted provider account and retain opaque denial metadata. Operator artifacts stay private; no operational IDs or secret values belong in the repository.

`pnpm preview` creates separate disposable anonymous databases and a synthetic authority; it does not provision provider resources. Shared web review still uses a Tailscale URL. The public production bundle has no fixture, restore, key or operator endpoint.

## Trusted restore protocol

Use `hosted/src/recovery-operator.ts` through a trusted binding-only operator context, or execute the equivalent SQL with the native D1 query API. No public production maintenance endpoint is required. Serialize operator actions, verify exact resources and read every mutation back before continuing. Never restore the owner-bearing test database for an acceptance experiment.

1. Inventory all payload copies and original-deletion deadlines, current plan/backend/history window, keys, exact app/recovery database IDs, deployed bundle and actor namespace. Preserve actual owner resources. Capture only a **native bookmark**, not a routine SQL payload export. Resolve its exact timestamp through the provider and verify it falls in a clean interval within seven days. The backend/history evidence is independent of the application test.
2. Read the pinned `recovery_head` and checkpoint. `closeRecovery(env, expectedCheckpoint)` conditionally closes it and records `recovery_interval`. Equivalent native SQL starts with `UPDATE recovery_head SET gate='closed',closedAt=? WHERE authorityId=? AND checkpoint=? AND gate='open'`; read back exact head, then insert its `(epoch,closedAt)` interval with `INSERT OR IGNORE ... SELECT`. A partially completed close stays closed. Confirm the interval exists before proceeding.
3. Wait for **zero actual `recovery_lease` rows**. There is no expiry/timeout that establishes drain. New public HTTP/authentication/mail/MCP returns 503; existing admitted child actor work can finish. If an execution disappeared leaving a lease, independently establish it stopped before any reviewed cleanup; otherwise leave recovery blocked. Do not clear leases based on age. Existing unrestricted class-date ranges remain supported.
4. `sealRecovery(env, checkpoint)` records an immutable latest security snapshot from the drained **pre-rollback** database. Native inventory queries are `SELECT p.userId,p.role,p.status,p.accessGeneration,c.revision FROM portal_participant p LEFT JOIN portal_aimharder_connection c ON c.userId=p.userId`, `SELECT role,publication,deletion FROM portal_activity_policy`, and `SELECT clientId,disabled FROM oauthClient`. Store exactly `{users,policies,clients}` in `recovery_snapshot(checkpoint,value)` with a plain `INSERT`, never replacement. No emails/hashes/tokens/envelopes belong in this snapshot. An existing seal is read back, never overwritten from a restored projection.
5. `authorizeRestorePoint(env, checkpoint, bookmark, targetAt)` rejects future/older-than-seven-day points and every closed/dirty interval, including undo points from a prior restore. It records one immutable `recovery_restore` row. The operator must independently prove native bookmark/time correspondence; local validation cannot do that. Perform **one** native restore only after these conditions. On uncertain provider outcome, inspect state/bookmarks instead of blindly repeating it. Access remains closed while old rows are present. D1 and DO restoration are separate operations.
6. Apply reviewed schema migrations as needed, preserving the independent gate and exact current manifest. Reconcile current tombstones, current status/policy/client state and permitted connection revisions using `reconcileRecovery`. It invalidates all restored auth sessions/code/reset/grant/consent state and executable journal records. It disables restored passwords; fresh maintained recovery or Google proof is required. It preserves only connections matching the latest sealed owner/revision, with no credential snapshots in the authority. Confirm older ciphertext can be authenticated with escrowed keys and, if needed, rewrap it with the existing reviewed vault command before key retirement. A mismatched/missing revision is removed and needs a fresh connection.
7. Check cleanup, latest head/seal, application checkpoint, exact status/policies/revisions and public closed-gate denial. `openRecovery` requires the application marker `(epoch+1,checkpoint)`, zero leases and the unchanged independent checkpoint. It advances the independent epoch; warm account objects discard clients/preparations. Read back open head/epoch, closed interval end and marker. Test deleted-account/session/code/refresh/grant denial, fresh unaffected proof/current connection and no old-reference replay. Restored pending invitations are invalidated and need a fresh invitation. No lifecycle operation sends a sporting mutation.

For native API cleanup, use the offline command:

```sh
cd hosted
node scripts/prepare-recovery.ts < /protected/latest-recovery-manifest.json > /protected/recovery-plan.json
```

The private input pins distinct UUIDs `applicationDatabaseId` and `recoveryDatabaseId` and contains `authorityId`, `checkpoint`, `epoch`, `closedAt`, literal `gate: "closed"`, literal `leases: 0`, immutable `snapshot`, `deletedUsers` UUIDs, `deletedInvitations` UUIDs, the recorded `restore` `{bookmark,targetAt,authorizedAt}`, all `intervals` `{closedAt,openedAt}`, literal `backendRecoverableDays: 7` and `copiedDeletedPayloads: false`. Obtain these from fresh trusted native queries, not assumptions. The last two declarations require separate provider/copy evidence. The command validates shape, clean intervals and age and emits native `{sql,params}` objects. It contains no credentials and performs no network/mutation.

Immediately reread the independent closed/drained checkpoint before executing. Compare both exact provider database UUIDs with the reviewed allowlist/bindings, and use only the exact `authorizedNativeRestore.bookmark`/provider timestamp; a matching display name is insufficient. Execute `authDatabaseStatements` sequentially against the exact application database; interrupted cleanup remains closed and is idempotently resumable. The application checkpoint statement is last. Read back its exact expected value and all cleanup conditions before reopening. Do not equate separate HTTP queries to `D1.batch`; the [REST contract](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/query/) supports SQL/batches but does not document a cross-request transaction guarantee. Native reopening changes the head only after all postconditions; write/read the interval end afterward so an interrupted interval close conservatively excludes extra restore points. Leave the gate closed on any mismatch.

## Retention/copy policy and evidence limits

The maximum is anchored to **original deletion**, never to export, re-encryption or restoration. With an actually verified seven-day Free D1 window, only clean restore points, no payload export chains and cleanup before reopening, a pre-deletion point can reintroduce a transient old row for at most another seven days: at most fourteen days from original deletion. The authority rejects dirty quarantine points to prevent chaining transient copies into a new history generation. This argument must be checked against actual provider bookmark/window semantics. It does not claim physical forensic erasure or that a new snapshot has aged thirty days.

Do not retain routine SQL dumps, staging/import payloads, copied databases or disk backups containing deleted data. If an exceptional copy is necessary, inventory it and enforce a deadline no later than original deletion plus thirty days; restoration cannot refresh it. Email-provider delivery records and local operator artifacts are separate copies with separate actual retention evidence. Keys remain outside database contents; retaining a global recovery key is not proof that deleted ciphertext expired. The #74 actual independent-key/rotation/new-key-only recovery evidence covers custody, not deletion-safe database restore.

The account actor durably stores only opaque ownership/alarm metadata; no credentials, cookies or executable preparation is stored there. The D1 journal is cleared on deletion/restore. Never restore a deleted actor as a source of credentials or permission. Actual DO PITR requires a separate isolated synthetic-only test/helper and independent gate/epoch checks; local workerd does not prove native PITR behavior. Preserve provider evidence separately from public application fixtures.
