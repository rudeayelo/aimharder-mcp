# ADR: hosted MCP client authorization and revocation

Status: accepted engineering implementation for [#73](https://github.com/rudeayelo/aimharder-mcp/issues/73), locally verified on 2026-10-18. Complements the [hosted identity decision](2026-10-15-hosted-identity-and-credential-custody.md), [runtime candidate](2026-10-16-proposed-cloudflare-hosted-runtime.md) and [isolated feasibility boundary](2026-10-18-isolated-worker-authentication-feasibility.md). Actual ChatGPT/Hermes and production-pilot acceptance remain outstanding.

## Context

The feasibility slice proved the maintained OAuth/JWT/SDK combination, but had no browser consent UI, operator registration workflow or participant client controls. The maintained resource wrapper verifies JWT cryptography and claims without consulting application admission/revocation. Deleting provider consent alone leaves signed access tokens usable. Revoking one client must preserve other clients and the stable portal identity, and a concurrent refresh must not revive revoked authorization.

## Decision

Keep Better Auth/MCP 1.7.10, its maintained sign-in, signed OAuth query, PKCE, code exchange, refresh rotation and JWT verification. Keep the private SDK v2 HTTP package separate from SDK v1/local stdio. Add browser consent, fixed-origin login continuation, a participant connection list and same-origin individual revocation.

Canonical JWKS routing amendment, 2026-10-19: enable `global_fetch_strictly_public` in the production Worker deployment configuration. The maintained verifier retrieves keys from the same canonical custom domain. [Cloudflare documents](https://developers.cloudflare.com/workers/configuration/compatibility-flags/#global-fetch-strictly-public) that without this flag own-zone global fetch targets the origin, while the flag uses the public front door and may re-enter the same Worker. Actual ChatGPT OAuth succeeded, but discovery raised a maintained JWKS exception/500 despite a successful external JWKS read; a fresh synthetic unknown-key token reproduced the 500 at the public boundary. Preserve maintained signature/issuer/audience/scope validation and current grants rather than add an application key-fetch substitute or relax authorization. The separately reviewed flag-only rollout retained the exact executable/resource/custody/security state, and the same negative token now receives 401. Actual ChatGPT then discovered all 18 expected tool names and completed authenticated account-context calls; a bounded trace confirmed canonical JWKS 200 and the intended MCP call 200 without exceptions. This resolves the observed routing defect, not the remaining full client/cost gates. Exact wire revision remains unobserved; local fixture adapters are not provider-routing evidence. See the [actual correction record](../hosted-mcp-authorization.md#actual-chatgpt-discovery-defect-and-proposed-routing-correction-2026-10-19).

Offline-access resource-policy amendment, 2026-10-19: preserve `offline_access` alongside `mcp:access` in the configured resource allowlist. The globally supported/requested client scopes already contain offline access; the resource intersection had removed it from persisted refresh scopes. The maintained [provider documentation](https://github.com/better-auth/better-auth/blob/main/docs/content/docs/plugins/oauth-provider.mdx) and pinned 1.7.10 session-deletion hook preserve only refresh tokens carrying that scope across portal logout. A fresh native production-migration reproduction matches the observed ChatGPT failure: sign-out marks the narrowed online refresh revoked; its later first refresh returns 400 and deletes the family while the application grant remains current. Preserve maintained logout, scope filtering, token verification and rotation instead of introducing a custom revocation exception. Protected MCP still requires `mcp:access`; protected-resource metadata is unchanged. The existing `resourceSeedMode: 'merge'` upgrades the configured D1 resource policy, without changing any issued token's scopes or revocation. Old online/revoked grants require fresh personal consent; no old row is repaired or revived. Portal password reset may still end browser sessions, but is not a substitute for explicit MCP client revocation, participant suspension or account deletion. Those existing current-grant/generation/admission guards remain authoritative. Anonymous upgrade/sign-out/default-expiry/SDK rotation and replay checks pass. The reviewed 98da176 rollout is now verified with matching deployed bundle digest and persisted resource-policy upgrade; existing token/grant/revocation state is unchanged. Fresh Hermes personal authorization now has a successful owner callback, normal maintained CLI return, independent original-administrator/static-client/resource-scoped new offline-family/current-grant read-back and subsequent maintained 18-tool/account-context success. The later [ChatGPT checkpoint](../hosted-mcp-authorization.md#chatgpt-reauthorization-and-rendered-context-checkpoint-2026-10-19) now records owner-completed reauthorization, connected browser return/rendered context answers and separate provider-only original-administrator/offline-family/current-grant evidence. It does not establish unique retry issuance, wire dispatch or actual normal-expiry renewal; the later [Hermes default-policy trial](../hosted-mcp-authorization.md#actual-hermes-default-policy-refresh-2026-10-19) independently passes protected context plus same-original-grant rotation after portal sign-out under the unchanged one-hour policy, with no new consent. Decoded JWT expiry/token HTTP/wire grant type remain unobserved, and ChatGPT renewal remains open. See the [correction evidence](../hosted-mcp-authorization.md#portal-sign-out-and-offline-refresh-correction-2026-10-19).

Chrome applies `form-action` to submission redirect chains. Preserve the separate Google-form opt-in, and allow MCP consent to redirect only to the origin of its exact registered callback (HTTPS ChatGPT or fixed HTTP loopback). Deny an altered/unregistered callback before rendering that policy. Full callback/PKCE/signed-state checks remain in the provider. HTTP CSP assertions are not native browser handoff acceptance.

Provision public PKCE clients offline through trusted operator review of an exact ChatGPT or Hermes callback and the configured environment's resource. No shared client secret is needed. Keep DCR and all client-creation privileges disabled; do not install CIMD or fetch arbitrary metadata URLs. Current official [OpenAI authentication](https://developers.openai.com/plugins/build/auth), [provided-client manifest](https://developers.openai.com/plugins/build/plugins) and [Hermes configuration](https://hermes-agent.nousresearch.com/docs/user-guide/features/mcp) document this setup direction. A particular real UI/version must still be validated. If a supported client cannot use this path, leave compatibility unresolved rather than silently weaken network/registration policy. A public client name/ID is not software attestation.

Use the provider's configurable token-storage hook with SHA-256 hexadecimal digests for authorization codes/refresh tokens. Add an application grant ledger keyed by the original code digest. The maintained token hook resolves a verified user and original grant; refresh retains that grant identity. Signed access tokens include a namespaced grant ID in addition to provider-owned subject/client/audience claims. Snapshot the authenticated participant’s persisted client-revocation generations before maintained consent processing. Carry the selected client generation in the private authorization-code verification metadata and original grant. Capture it once per HTTP request: the maintained consent endpoint redispatches authorization internally, and that continuation must not adopt a later generation. Generation equality, never native verification timestamps or process clocks, fences issuance. Password hashing and non-OAuth verification formats remain maintained defaults.

Check current verified active admission, client enablement and matching unrevoked grant on every protected MCP request after maintained JWT verification. Revocation atomically increments this participant/client’s persisted integer generation, marks its grants revoked and removes its provider refresh/access tokens and consent. Grant insertion conditionally requires the captured generation to equal the current generation in the same D1 statement; every protected call checks that equality again. Tombstones are never reset by issuance; a racing refresh can at most issue an unusable token tied to its revoked original grant. Every new authorization uses the maintained `prompt=consent` before signing its continuation; ordinary refresh is unchanged. This prevents a delayed old consent write from silently reconnecting a later authorization. A later explicit consent gets a new grant identity, preserving denial of previous JWTs. Connection listings use the same current-generation grant boundary, joined to enabled client and maintained consent for this participant. A stale consent row alone never appears connected; pending unexchanged approvals appear only after a usable grant is minted. Portal account identity and other clients are untouched. Grant/generation records cascade with portal identity deletion; later lifecycle/restore work must preserve revocation beyond backups.

Use the general `mcp:access` resource scope before real client onboarding, replacing the earlier feasibility-only `mcp:read` scope. The maintained resource seeder merges only the configured MCP resource's declared name/allowlist so existing feasibility rows adopt this scope; unrelated resource policy remains untouched. OAuth service access never confirms an upstream action: later full-feature tools must retain role checks, exact previews, separate confirmation and read-back. Initially expose only the account-context tracer until the vault/coordination/tool slices. The later [schedule-query extension](../hosted-schedule-queries.md) adds its four existing reads through the verified subject-owned account boundary for both roles. The [personal activity/RM extension](../hosted-activity-queries.md) adds its four existing own-account reads through the same boundary. Return a safe unconnected outcome without shared upstream credentials or write tools. The [client runbook](../hosted-mcp-authorization.md) records routes, setup, library lifetimes/refresh overlap and evidence boundaries.

## Consequences

Migration `0004-mcp-grants.sql` is required before this version handles OAuth. Older feasibility client registrations must be reprovisioned for the service-access scope, and tokens lacking the scope/grant claim require reauthorization; existing portal identity, passwords, verification and invitations remain intact. The already initialized test D1 requires explicit reviewed migration application, not replay of its initial schema or unadopted Wrangler migrations.

The ledger adds authoritative D1 reads and minimal grant/revocation state. It provides application client revocation beyond a stateless JWT's remaining lifetime. Immediate revocation is the portal operation; local cache deletion or consent deletion alone is not equivalent. OAuth authorization policy is separate from AimHarder connection replacement, which must continue preserving current client grants while invalidating upstream sessions/actions under later tickets.

Twelve new actual HTTP/workerd/D1/SDK tests cover the accepted authorization seam, including a real loopback callback listener, current admission, invalid state/resource/verifier, concurrent refresh/revoke, delayed code insertion, authorization while a revocation batch is pending, and a consent write delayed past revocation. Scheduling fixtures pause real D1 operations without replacing policy data. The stale-consent regression was red both when an internal continuation adopted the new generation and when a later authorization reused restored consent; immutable request snapshots and fresh maintained consent close both paths. There are no auth mocks or real credentials. The isolated code-only deployment and migration were subsequently observed as recorded below; actual ChatGPT/Hermes callbacks, supported plans/settings, full query/action journeys, load/cost and lifecycle restoration remain separate acceptance gates. This decision authorizes no purchases, plan changes, production launch or AimHarder writes.

## Confirmed-write dispatch check (2026-10-19, issue #77)

The [coordination decision](2026-10-19-confirmed-hosted-action-coordination.md) carries verified grant/client context per execution request to the owning account object. Immediately before a booking fetch, one authoritative D1 query requires current active verified admission, unrevoked current-generation grant, enabled client and the original connection revision. Current-grant queries also evaluate participant admission in that same query. A reused upstream client never stores an MCP client's authorization permanently. No new scope, registration mode, role switch or public identity selector is introduced; already admitted/sent external writes cannot be undone by later revocation. Actual client and later lifecycle acceptance remain separate.
