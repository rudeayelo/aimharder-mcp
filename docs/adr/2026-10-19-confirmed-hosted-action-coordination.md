# ADR: confirmed hosted action coordination

Status: accepted on 2026-10-19 for [issue #77](https://github.com/rudeayelo/aimharder-mcp/issues/77). Local synthetic implementation; platform schema/code activation and actual ChatGPT/Hermes acceptance remain separate.

## Context

The [account object](2026-10-19-encrypted-aimharder-account-boundary.md) owns an upstream client and serializes complete operations. Its queue and the local client's preparation store cannot alone record whether an interrupted hosted write may have been sent. The first remote write must preserve the [existing booking execution](2026-09-25-booking-creation-execution.md) and [single creation confirmation](2026-10-07-booking-creation-without-credit-warning.md), while providing coordination for later cancellation, activity and connection/access lifecycle tickets.

## Decision

Keep the complete prepare/execute/read-back operation in the subject-owned `AccountConnection` queue and real client. Expose the existing two strict booking-creation tools to both roles without a switch. The caller supplies no identity, source ID, credentials or URL. The exact preview and separate account-holder confirmation remain mandatory; `confirmed: true` alone does not establish human consent. Creation has no extra credit acknowledgement.

Add an internal `AccountActionCoordinator` module. Its bounded in-memory preparation binding includes action, portal ownership through the actor, pinned upstream identity, semantic connection revision, verified gym and two-minute expiry. The client's original reference retains the exact target/source and account/membership binding. Lost preparation always requires a new preview and confirmation.

Persist only consumption/recovery records in D1 `portal_action_journal`, keyed by portal subject and SHA-256 reference digest. Await consumption before preflight. Immediately before the private `fetch`, after constructing cookies/body, persist `possibly-sent` with minimal encrypted original dispatch facts and then check current verified active admission, current grant/generation/client and exact connection revision together in one D1 query. Check reference expiry again after that awaited authorization. A known denial is a zero-send error outside the transport-failure catch. The successful guard is the dispatch admission point; later revocation cannot unsend an already admitted external request. Later lifecycle changes must use the same actor queue/guard contract, rather than claiming the external write and D1 can share a transaction.

The AES-256-GCM journal envelope uses a distinct `aimharder-action` purpose plus portal subject, revision, action/reference digest and key ID as authenticated data. Original identity, membership/source target and preview are encrypted. Only denial/response-issue interpretation flags are added after dispatch, preserving rejection/conflict semantics across restart when that update succeeds. A post-send bookkeeping failure cannot skip original-account read-back: return its honest current result and disclose unavailable recovery details. A later terminal-phase update/cleanup failure leaves the prior durable fence intact and cannot replace an already reconciled result with a generic request error. If response flags were not persisted, later recovery may be less conclusive; it never invents rejection or resends. No credential snapshot, cookies, raw upstream response, full result or sporting-history mirror is retained. Maximum live records per account is 64; refusal requires fresh preparation after capacity expires. Records expire ten minutes after consumption; account alarms and subsequent execution sweep expired records. Global trusted D1 maintenance also purges expired records. Expiry removes recovery facts, never establishes that a possible external write did not occur.

A different actor instance can consume a retained recovery record for read-only reconciliation through the original pinned client contract. It never reinstates local preparation or calls a sporting write. Fresh original-account schedule/upcoming reads may confirm a current state; absent response/denial evidence never turns an unbooked state into a rejection. If the original revision/identity cannot be used, report uncertainty using the original protected target, without reading a replacement account or restoring old credentials. A lost, expired, foreign or already consumed reference never authorizes another dispatch.

Use D1 for the journal instead of private object storage so the existing trusted operator path can inventory, conditionally rewrap and inspect all active ciphertext. Extend the offline rotation command to accept `{ connections, actions }`; retain connection-array compatibility but mark that it lacks action inventory. Exact old-ciphertext/revision/action/reference predicates protect concurrent updates. Completion changes the phase without overwriting concurrently rotated facts. Active-key-only recovery must cover both inventories before runtime key retirement. Old escrow stays available for retained encrypted copies; this does not implement backup retention or deletion-safe restoration.

## Alternatives and consequences

A queue alone loses consumed/sent state on eviction. Persisting executable preparations would revive permission after restart. Copying upstream HTTP into hosted code would duplicate source validation/reconciliation. Persisting old credentials for recovery could revive disconnected or deleted access. Private object-only journal storage would require a new unproven operator inventory path; D1 reuses the established restricted operator seam at the cost of bounded extra reads/writes.

The shared client adds only trusted execution/reconciliation interfaces; local MCP inputs, outputs, eighteen tools, account scope and upstream request algorithm remain unchanged. Production activation must apply migration `0006-action-journal.sql` before the new bundle. No actual booking, cancellation, provider mutation, purchase or plan change is authorized by this decision. Later activity policy, replacement/disconnection, suspension/deletion and independent restoration authority remain their own tickets. The D1 journal is not an independent deletion/revocation authority outside a restored authentication database.

[Cloudflare D1 documentation](https://developers.cloudflare.com/d1/worker-api/d1-database/) describes the awaited database interface and transactional batches; the account queue orders this application's operations. [Durable Object alarm documentation](https://developers.cloudflare.com/durable-objects/api/alarms/) describes cleanup scheduling. Neither primitive makes an external AimHarder request transactional or supplies exactly-once upstream execution. Synthetic tests and separate deployment/client evidence are recorded in the [runbook](../hosted-booking-creation.md).

Implementation update for [#80](https://github.com/rudeayelo/aimharder-mcp/issues/80): [hosted own-activity deletion](../hosted-activity-deletion.md) now reuses the same coordinator and fault-preserving read-back contract. Its journal stores only identity, box/gym, entry ID/date and interpreted response status, excluding full entry content. Current deletion policy joins the final grant/revision query; restart recovery verifies supplied source/gym selectors against protected original facts and cannot dispatch. The local eighteen-tool stdio contract and upstream deletion evidence limits remain unchanged.
