# ADR: encrypted AimHarder connections and an account operation boundary

Status: accepted implementation decision on 2026-10-19 for [issue #74](https://github.com/rudeayelo/aimharder-mcp/issues/74). Local synthetic validation and subsequent owner-managed key custody/isolated namespace activation are recorded separately in the [connection runbook](../hosted-aimharder-connection.md). Owner-reported deployed connection, independent ciphertext validation and controlled conditional rotation/active-key-only runtime recovery are recorded there. The owner separately reported continued public connection after the new-key-only recovery rollout, completing this slice's acceptance. Full backup/lifecycle restoration is outside this evidence.

## Context

The [identity/custody requirements](2026-10-15-hosted-identity-and-credential-custody.md) accept service-recoverable upstream credentials, one linked AimHarder account and separate portal/client identities. The [runtime candidate](2026-10-16-proposed-cloudflare-hosted-runtime.md) requires explicit per-account coordination and disposable sessions. Returning plaintext configuration to a stateless MCP handler and constructing a client per invocation cannot preserve cookie/failure isolation across requests or establish the later action boundary.

## Decision

Route only a verified, currently admitted portal/OAuth subject to the private `ACCOUNT_CONNECTIONS` binding. Export the ordinary `AccountConnection` Durable Object class, with a SQLite namespace, and derive its name from that stable portal subject. The object records its owner and serializes whole operations with an explicit promise queue; it does not hold network I/O inside `blockConcurrencyWhile`. Separate objects progress independently. This selects the candidate account boundary for read-only #74; it is not an MCP session or a complete durable write coordinator.

D1 is the authority for one encrypted connection row per portal identity. The row contains a generated semantic revision, encrypted envelope and update timestamp. Encrypt the complete username/password/configuration and verified numeric upstream identity with Web Crypto AES-256-GCM, a fresh random 96-bit IV and authenticated data containing purpose, version, portal subject, revision and key ID. Neither username, password, upstream identity nor key is a plaintext database column. No cookies, raw upstream response or sporting-history replica is persisted.

Use an independent versioned key ring in platform secret `VAULT_KEYS`, with `VAULT_ACTIVE_KEY_ID` selecting new encryption. Keep an authorized recovery copy in separate operator custody, outside D1 backups and separate from `AUTH_SECRET`. Imports are non-extractable. Missing/wrong keys, unknown envelope versions, modified/cross-tenant ciphertext and authentication-tag failures fail closed. Never generate keys or reinterpret ciphertext on startup.

The trusted offline `vault:prepare-rotation` command reads only encrypted rows on stdin, takes keys through its environment and prepares new ciphertext plus conditional SQL. It preserves semantic connection revision and updates only the exact prior envelope/revision; stale maintenance output cannot overwrite a later settings change. Apply this private artifact through the existing authorized D1 operator path. No public maintenance/key endpoint or administrator credential-viewing privilege is added. Root operator activation and recovery escrow must be verified separately; application tests cannot establish platform custody.

Initial connection verifies identity/memberships with the real API client before committing ciphertext. Several gyms require an explicit verified default. Time zones retain assumed Europe/Madrid or explicitly confirmed IANA mappings. The trusted client `verifyConnection()` exposes numeric identity only inside the service and pins it; the optional expected identity guards fresh sessions after restart. Public MCP results retain their previous identity-free schema. Different portal/upstream email addresses are supported. The initial #74 slice rejected replacement with 409; the [#81 lifecycle amendment](2026-10-19-upstream-connection-lifecycle.md) now adds explicit verified replacement/password/disconnection; settings updates can change only verified gym configuration, preserving portal/client authorization.

Each account object owns one in-memory API client per current connection envelope/revision. On restart it decrypts D1, constructs an empty session and verifies the pinned upstream identity. Authentication failure stays local to that client. All existing fixed origins, redirects, body limits, timeout and bounded reauthentication safeguards remain in the shared client. Current admission is checked again at the account boundary, in addition to the MCP grant checks.

Separate own-account membership discovery/status from selected-gym MCP query validation. If a changed membership makes the default missing or inaccessible, return safe `selection-required` status with current verified choices and keep the settings form available, without requesting stored credentials again. Require an explicit accessible selection; MCP retains its original missing/inaccessible-default errors until repair. The same owned client checks the pinned identity before any membership is displayed; this is not a fallback to another account or an inferred default.

## Alternatives and consequences

A module-global client cache cannot provide a reliable tenant/operation boundary or survive eviction. Reimplementing upstream authentication would duplicate the verified API client and weaken its contract. Storing plaintext credentials in an actor/database or deriving the vault key from an authentication secret would not satisfy separate recoverable custody. D1 atomic coordination remains a possible alternative, but would need an equivalent operation-ordering design.

This decision partially implements the earlier runtime/custody requirements; it does not supersede their lifecycle, role, backup or real-client requirements. Preparation state, dispatch fencing, durable action consumption and original-account reconciliation must be added before any hosted sporting write. Replacement and disconnection are now implemented by the #81 amendment linked above; suspension/deletion and restoration that preserves later revocations remain separate tickets. Losing in-memory state requires fresh authentication/preparation, never reconstruction of write permission. Key-only rewrap may drop the in-memory session safely; it does not change client grants.

The maintained portal/Google/Resend/MCP authorization implementation remains intact. SQLite-backed object availability on Free does not establish usage/cost or the EUR 10 target. Local validation alone establishes no purchase, plan change, namespace deployment, live credential submission or upstream write. The separate operator activation record establishes this isolated account’s key custody and namespace/schema/code deployment without changing this decision; owner-reported connection and independent ciphertext validation are recorded separately, with subsequent conditional rotation/active-key-only runtime recovery recorded there. The owner separately accepted continued public connection after recovery; this does not establish full D1 backup restoration, deletion/revocation-safe restore or backup retention enforcement.

## Remote schedule-query extension (2026-10-19, issue #75)

Route the existing class schedule, published workout, upcoming-booking and booking-history queries through this same subject-owned client and operation queue. Reuse the local strict schemas and successful results at the SDK v2 HTTP boundary; both portal roles have these reads without switches. Keep the full published-workout query, including own-account RM enrichment and its single recovery allowance, inside one account operation. A private `{ status: 'queried', result }` envelope prevents collision with the existing workout's public `status`. The remote layer adds no upstream endpoint, sporting-history store, identity selector or new local behavior. The [remote guidance and synthetic validation](../hosted-schedule-queries.md) record role/isolation, partial coverage and recovery evidence; actual ChatGPT/Hermes acceptance, deployment of this extension and later action/lifecycle guarantees remain separate.

## Remote personal activity and RM extension (2026-10-19, issue #76)

Route personal activity, known-ID/name-based 1RM and RM progression through the same subject-owned client and whole-operation queue. Name discovery and its selected personal detail remain one operation. Reuse the existing strict input/output schemas and API client without another member selector, inferred identity/unit, new upstream endpoint or persistent sporting-history store. The private queried-result envelope also preserves the existing RM/search public `status`. Both portal roles retain these reads. The [usage and synthetic evidence](../hosted-activity-queries.md) preserve 31-inclusive-date windows, recovered partial coverage and entry semantics; actual client acceptance and later write/lifecycle coordination remain separate. This extends the established boundary rather than changing its architecture or the existing activity/RM decisions.

## Confirmed creation extension (2026-10-19, issue #77)

The [confirmed-action coordination decision](2026-10-19-confirmed-hosted-action-coordination.md) now adds the first remote sporting write with durable D1 consumption/dispatch facts, current per-request admission/grant/revision checks and original-account read-only recovery. It resolves the earlier required preparation/dispatch foundation for creation; subsequent cancellation/activity/lifecycle behavior remains pending. Journal facts use distinct encrypted authenticated context without credential snapshots and join the trusted key inventory/rotation procedure. The account object still owns and serializes the whole real-client operation.
