# ADR: invited password admission and transactional email

Status: accepted implementation decision on 2026-10-18 for the local portion of [ticket #71](https://github.com/rudeayelo/aimharder-mcp/issues/71). Real sender activation, DNS configuration and delivery remain pending; this decision does not authorize them or a deployment. Complements the [identity requirements](2026-10-15-hosted-identity-and-credential-custody.md) and [Worker feasibility boundary](2026-10-18-isolated-worker-authentication-feasibility.md).

Subsequent authorization: the user approved creating an isolated Cloudflare test environment without purchases or plan changes. The [test-environment decision](2026-10-18-isolated-cloudflare-test-environment.md) records that separate boundary; actual sender setup/delivery is still unresolved and is not implied by a disabled-mail deployment.

## Context

Better Auth owns password hashing, verification tokens, sign-in, recovery and session revocation. A separate application admission record must prevent public signup, wrong-email acceptance, expired/revoked invitations and recovery-based admission. D1 has atomic batches, without interactive transactions. Better Auth 1.7.10 defers `user.create.after` until signup completes and catches email-callback errors; neither behavior can be treated as a transactional admission grant or a delivery acknowledgement.

Default verification JWTs identify an email rather than a stable user/invitation generation. They may be identical when created for the same email within one second. A digest of that JWT alone would therefore fail to distinguish a revoked pending identity from a new invitation to the same address.

## Decision

- Retain maintained Better Auth email/password and its default scrypt; require email verification and disable automatic sessions at signup/verification. Gate direct native auth routes and all identity creation with a current invitation for the same lowercase email. Do not invent email aliases. Application roles are server-owned.
- Store invitation capability digests, seven-day expiry, revocation and acceptance in D1. Store pending identities and durable participants separately. Ordinary invitations grant `user`. The trusted offline bootstrap creates one `admin` invitation; a unique partial index prevents a second owner bootstrap. There is no public bootstrap or role-selection route.
- Require a successful conditional invitation claim before Better Auth marks the email verified. Claim and participant insertion are one atomic D1 batch; revoke conditionally updates the same invitation only while unused. The first successful claim/revoke determines the outcome. Repeated verification is idempotent for the same identity. Every new session, protected portal page/admin request and MCP invocation checks current active participant admission and verified email.
- Add a random per-delivery capability to the native verification URL. Store only its combined digest with the native JWT, stable user ID and invitation ID. Better Auth verifies its own JWT; the callback checks the complete delivered capability against the current identity before claiming admission. Old verification deliveries cannot verify a recreated pending identity, even if native JWTs happen to match.
- Bind pending admission in the verification-send callback as well as the deferred creation hook. A new invitation can replace an unverified, unadmitted identity only when its earlier invitation is revoked or expired. A conditional D1 delete protects against concurrent admission; the fresh identity has fresh credentials and delivery capability. Existing admitted identities are never replaced through signup.
- Recovery is available only to a currently active, verified participant who already has a maintained credential account. It cannot admit pending/revoked identities or silently add password login to a social-only identity. Preserve generic recovery responses and stable user IDs; maintained reset consumes its token and revokes existing sessions before updating the password. Google and explicit linking remain [ticket #72](https://github.com/rudeayelo/aimharder-mcp/issues/72).
- Use Cloudflare Email Service's native structured `EMAIL.send` binding, restricted to the selected verified sender. This avoids requiring another provider account and uses the existing Workers Paid candidate. Missing binding/sender disables enrollment, resend and recovery with a uniform safe unavailable outcome. Track verification callback delivery failures per request and return unavailable despite Better Auth's callback-error suppression. With a configured sender, recovery retains the same generic HTTP status/message for eligible and ineligible addresses even when sending fails, preventing disclosure of account/password eligibility. Its HTML result explicitly conditions receipt on eligibility and delivery availability rather than claiming that mail was sent. Provider errors, links and tokens are never logged or exposed in admin listings.
- Keep the email capability only at the external delivery boundary. Local workerd tests substitute that boundary in a separately bundled fixture entry; the production entry has no fixture provisioning or captured-mail route. The offline owner command creates a fresh private directory outside the checkout under an existing trusted parent, then writes digest-only SQL and a private delivery artifact with restrictive permissions and no capability output. It rejects existing output directories before writing and never changes their permissions. It applies and sends nothing.
- Render forms with `Referrer-Policy: strict-origin`: only the origin can be sent as a referrer, protecting URL capabilities while preserving the browser's same-origin POST Origin header. `no-referrer` caused actual Chrome form submissions to send `Origin: null` during local browser QA and fail the origin check. Continue rejecting null, missing and foreign origins on application POST routes.

## Consequences

The local public HTTP surface now supports invitation administration, acceptance, verification, sign-in, resend and recovery without custom password authentication. An administrator can see invitation recipient/status/expiry, without sporting data or diagnostics. Failed delivery revokes an undelivered invitation; an already-created pending account can resend verification while its invitation remains valid.

If a native verification write fails after a successful admission claim, verified-email checks still prevent access; a new verification delivery for the same accepted identity remains possible after invitation expiry. Admission and maintained verification are deliberately distinct. If a maintained password reset fails after token consumption on non-transactional D1, it fails closed and requires a new recovery link; rollback is not promised.

[Cloudflare pricing](https://developers.cloudflare.com/email-service/platform/pricing/) currently includes 3,000 outbound messages/month on Workers Paid, then USD 0.35/1,000. The 20-participant planning allowance of at most 200 messages/month fits that inclusion. Sending is beta. A later authenticated dashboard inspection established Workers Free as the current plan, with Email Sending unavailable on Free and included on Paid, displayed at USD 5/month plus usage. No upgrade was selected. Native sending is blocked under the explicit no-purchases/no-plan-changes authorization; domain/sender verification, quotas, delivery, platform retention, deployed password-authentication CPU and measured total cost remain unverified. Local implementation tests used synthetic external data. A separate later read-only credential/provider inspection confirmed an active token/zone and limited resource access, with subscription and Email Sending reads denied; it created no remote environment or permissions and changed no DNS or billing. See [setup and evidence](../hosted-admission.md). The existing local stdio package, AimHarder API contracts and their live limitations are unaffected.
