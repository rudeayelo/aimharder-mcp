# ADR: manual booking writes for the next feature phase

Status: accepted for feature scope on 2026-09-24; the checkout's creation and cancellation flows are implemented under the [creation preparation decision](2026-09-25-booking-creation-preparation.md), [creation execution decision](2026-09-25-booking-creation-execution.md), [cancellation preparation decision](2026-09-25-booking-cancellation-preparation.md), [standard cancellation decision](2026-09-25-booking-cancellation-execution.md), and [late confirmation decision](2026-09-25-late-cancellation-confirmation.md). One standard creation/cancellation cycle at 9NBC was observed live on 2026-09-25; late and other branches remain unverified upstream.

## Decision

Extend the local MCP server beyond its read-only MVP with individual, explicitly requested booking creation and cancellation actions. Each action is limited to the authenticated account holder at a verified accessible gym. Family or other-account writes, bulk actions, and automation are outside this phase.

Require prior confirmation for each real write, with the gym, class, date, time, and intended action made explicit. Real validation may use a nearby Open Box class, but each creation and cancellation requires its own confirmation before execution. Do not make a booking merely to test connectivity without that confirmation. Read the booking state after each attempted write and report uncertainty rather than assuming success from an HTTP response alone.

Use a read-only preparation step that displays the target and issues a short-lived action reference, followed by execution only after the account holder confirms that specific action. Refresh the relevant source data immediately before execution and stop if the target or eligibility has changed. Do not accept an arbitrary source ID supplied without an unambiguous match to a recently retrieved class session or booking. Require a user-confirmed IANA gym time zone for writes; an assumed zone is sufficient only for the existing read tools. The confirmed zone for 9NBC is `Europe/Madrid`.

For 9NBC, the publicly stated penalty begins when a reservation is cancelled fewer than 90 minutes before class. Show the risk of losing a credit before the first cancellation POST when the gym-local start is at or inside that boundary; do not apply this gym-specific rule to other gyms. If AimHarder reports that a cancellation will lose a credit, stop and require a separate confirmation explicitly naming that consequence before a late-cancellation attempt. The account holder does not recall whether late cancellation is technically blocked or allowed with lost credit, so let the verified upstream response decide. The initial cancellation request may itself succeed, so it must never be used as a harmless preflight. For any write with an uncertain transport or response outcome, do not retry automatically, including after reauthentication. Query the current booking state first; if it remains uncertain, report that uncertainty and require a new preparation and confirmation before another attempt.

Defer joining and leaving a waitlist from the first write delivery until research verifies AimHarder's contract and the account's eligibility. Continue to represent observed waitlisted states distinctly from confirmed bookings. The account holder has not encountered waitlists personally, so their behavior is not established by experience.

The first delivery uses only the standard booking attempt; it does not use the `insist` parameter reported by unofficial clients or automatically retry a rejected booking. If the credit effect cannot be independently determined before a booking, disclose that uncertainty in the action preview and proceed only with action-specific confirmation. The account holder reports that at 9NBC a confirmed booking uses one credit and timely cancellation releases it, allowing repeated booking/cancellation; this is gym-specific user experience, not a verified API rule or a promise about late cancellation. The reported one-hour booking cutoff is not independently verified: warn near that boundary, but let AimHarder determine eligibility rather than hardcoding a rejection.

After cancellation, confirm only the booking state shown by a fresh read. Do not claim that a credit was returned unless a separate reliable credit balance or state check verifies it. The [credit-balance investigation](../research/2026-09-24-booking-credits.md) has not yet verified such an endpoint. The absence of a verified balance endpoint does not block manual booking writes, provided previews and outcomes disclose credit uncertainty.

If a balance query is later supported, report credits per verified subscription or session pack with its own validity and expiry; do not merge different credit sources into a presumed calendar-month total. The account holder reports a 15-session monthly subscription at 9NBC whose unused credits expire on the first day of the next month. They believe session packs may last about six months, but have not confirmed that duration or whether other gyms follow it. These are user reports, not validated API rules. An eventual query must distinguish the account holder's current monthly allowance from longer-lived packs using source-backed period boundaries.

For real validation, inspect the account's five-day booking window at test time and prepare the eligible Open Box class furthest in the future within that window, leaving the greatest available time to resolve a failed cancellation before the credit-loss boundary. Obtain separate confirmation for the booking, read its resulting state, then prepare and seek separate confirmation for its cancellation. The account holder explicitly confirms that their account can book Open Box; still verify that the selected class is offered to this account before the write. The public monthly 15-session tariff description alone does not establish Open Box eligibility for other accounts. If the selected Open Box cannot be verified as eligible, stop and present another class for separate confirmation rather than substituting it automatically. If cancellation remains uncertain, promptly show the unresolved reservation and remaining cancellation window to the account holder for direct action. If the upstream response warns that cancellation loses a credit, pause and show that consequence before any late-cancellation request. A test plan is not advance authorization for either write.

## Consequences

The existing MVP remains a read-only historical release; these actions are a later feature phase. The prior booking-read models do not establish a write contract or a reliable schedule-session join. Cancellation eligibility, source response handling, and live verification still require evidence. The server cannot prove that a person saw a prompt merely because a client supplies a confirmation reference; client behavior and tool descriptions must also require actual user confirmation.
