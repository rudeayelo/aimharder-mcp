# ADR: independent deletion authority and controlled restoration

Status: accepted implementation design on 2026-10-19 for [#83](https://github.com/rudeayelo/aimharder-mcp/issues/83). Synthetic application/operator evidence remains separate from the completed isolated [provider experiment](../hosted-restore-provider-validation.md). Its controlled restore, scheduled purge, recovery and scoped copy/retirement observations support #83; elapsed physical erasure, sustainable pilot capacity and production launch are not implied.

## Context

The [identity/custody requirements](2026-10-15-hosted-identity-and-credential-custody.md) require immediate account deletion and at most thirty days of earlier encrypted backups, anchored to the original deletion. Restoring `AUTH_DB` also restores its grant generations, connections, sessions and operation journal. Neither the [action journal](2026-10-19-confirmed-hosted-action-coordination.md) nor the [suspension generation](2026-10-19-hosted-participant-suspension.md) can independently establish current authority after its own rollback.

## Decision

Require a separate D1 `RECOVERY_DB` and pinned opaque `RECOVERY_AUTHORITY_ID`. Never roll it back with `AUTH_DB`. Its schema contains only opaque deleted-user/invitation tombstones, the latest sealed security manifest, nonexpiring request leases, a gate/epoch/checkpoint, projection deadline-audit IDs/completion and closed recovery intervals/bookmark metadata. No email, token, password/hash, encrypted credential copy, training content or raw HTTP response belongs there. Missing bindings, identity or head fail closed. An operator cannot substitute a new empty authority after losing the latest one and reopen restored data as if no deletion occurred.

Each production HTTP operation obtains an independent gate lease. Each owned actor operation also holds its own lease through its complete awaited result, covering early streaming transport headers. Root acquisition requires an open gate and no supplied parent. Every child acquisition requires its supplied parent to exist in the current epoch, even after reopening; an open gate never rescues an ended parent. HTTP entry and alarms explicitly acquire roots. An operation already admitted may create a child while its current parent remains live under a closed gate; an abandoned callback cannot acquire one after its parent ends. Closing the gate prevents new external admission. Restoration is allowed only after the actual lease count is zero. There is no lease TTL: class-date reads have no interval cap, and expiry is not proof of completion. Lost leases require independently establishing that the originating execution stopped; absent that evidence, do not clear them or restore. Alarms also obtain leases and perform no journal maintenance under a closed gate.

The independent authority check precedes the existing final atomic D1 grant/admission/role/revision query. That query remains the last awaited authorization before sporting dispatch. A completed close/drain cannot interleave with a still-leased dispatch or read-back. Ordinary deletion/revocation still linearizes against the current D1 guard; an already admitted external write cannot be unsent. Copy the provider environment per account actor; request-scoped lease state must not be shared across participants.

Deletion requires a current owner session, same-origin POST and explicit `confirmed: true`. Write opaque independent deletion and invitation tombstones before erasing the app projection. Remove the identity, linked Google/password methods, sessions, OAuth capabilities/grants, encrypted upstream row, journal and associated invitations/admission records. Generic maintained verification values can contain encrypted OAuth state that cannot safely be attributed; conservatively invalidate pending verification/reset/authorization transactions globally. Other established participants retain their sessions, authorizations and connections. If app cleanup fails, the independent tombstone already denies portal/MCP/sign-in/recovery; report cleanup pending rather than claiming complete deletion. Trusted cleanup is resumable.

Queue memory erasure after any original owned operation. A preflight that lost authorization sends nothing. A possibly sent action completes available original-account read-back using its already-owned in-memory client; deleted persisted credentials are never recreated. Then discard its client, executable preparations, owner metadata and alarm storage. Deletion sends no booking or activity mutation. Binding-only erasure is independently permitted only for an authoritatively deleted owner and is not a public maintenance endpoint.

Before a controlled rollback, close/drain and seal the latest opaque participant IDs/roles/status/access generations, semantic connection revisions, current method associations (`id`, owner, provider and opaque provider-account key), role-policy bits and client disabled flags. A seal is immutable for its checkpoint: rereading a restored projection cannot overwrite it. Authorize one native bookmark in a clean interval within the selected seven-day backend window, independently recording its provider-resolved time. The trusted operator must establish that bookmark/time correspondence; a supplied string is not provider evidence.

Reconcile under the closed gate with the latest manifest and deletion/invitation tombstones. Delete restored identities absent from that manifest or independently deleted; invalidate all restored sessions, generic verification/code state, grants/tokens/consents and action journals; revoke pending restored invitations. Delete restored method rows absent from the exact latest association allowlist, including a stale unlink/relink row with the same provider subject but a different association ID. Never reconstruct a newer missing method from metadata. Disable remaining old password hashes and require maintained fresh email recovery or unchanged Google proof. An unlinked credential method cannot gain recovery merely through a restored placeholder password. Reapply latest statuses/roles/policies/client flags, increase access generations beyond the drained manifest and advance the independent recovery epoch. Warm actors discard all preparations and clients when that epoch changes. A restored encrypted connection survives only if its AEAD-bound owner/revision matches the latest permitted revision. A replacement/disconnection after the backup therefore cannot revive an old connection. Key availability/authenticated decryption must be verified separately before reopening; older envelopes may need the escrowed previous key and reviewed rotation command.

This stronger restored-password/session/client invalidation is specific to rollback. Ordinary password recovery, independent client revocation, key recovery and connection replacement retain their existing behavior. Nondeleted profiles and provably current connection/configuration are preserved. If the latest independent head or pre-restore manifest is unavailable, do not reopen; no unverified fallback treats old credentials as current.

Use a trusted module and offline native-SQL plan, with no public restore/key endpoint. Worker `D1.batch` is atomic. The native REST query documentation supports batches/multiple statements but does not explicitly establish cross-request transaction semantics. Native operator execution instead applies idempotent cleanup stages while access is closed, with the application checkpoint marker last, exact readbacks and explicit reopening only after postconditions. Before full cleanup erases restored evidence, both binding and native operators record current residual deleted-user UUIDs against original independent deadlines. Their independent prelude marks overdue without blocking erasure; a completion postlude catches deadlines crossed during cleanup. The final application marker binds an audit UUID, and reopening requires the same independently completed audit. Native SQL evaluates at least its actual SQLite wall time so delayed execution cannot reuse a frozen preparation clock. A new native restore requires a fresh pre-cleanup inventory and plan. An interrupted cleanup remains closed and can resume; never replay a native provider restore merely because its response was uncertain.

## Original-deletion retention bound and remaining evidence

The selected operational policy permits only verified Free D1 seven-day history and clean restore points. Never restore a point within a recorded dirty quarantine interval or between an original deletion and its first confirmed purge. A restore can make forbidden old data current indefinitely if cleanup is abandoned: a closed gate protects access, not retention. The earlier fourteen-day argument is withdrawn because it did not bound that interval.

Configure a five-minute production Cron Trigger for tombstone-only deletion maintenance. It checks the actual current projection on every invocation, even after a prior success or another native rollback. It removes only authoritatively deleted identities/invitations and associated active data. It requires the pinned independent authority, but neither a public/drain lease nor a maintenance lock can block this sanctioned deletion. It does not reconcile nondeleted authentication, write the recovery marker or reopen. Persisted purges and independent health are completed for every tombstone before queued original-account memory erasure is handed to `ExecutionContext.waitUntil`; one unbounded original read cannot delay another account's credential purge. Full restoration still needs zero actual leases and the immutable latest seal.

Record each original deletion's cleanup deadline as deletion plus twenty-three days, durable per-tombstone `purgePending`, first confirmed purge, latest attempt/success and sticky pending/cleaned/failed/overdue state. Acknowledged pending evidence precedes any normal, scheduled or full-projection residual erasure and survives new audit IDs, failed completion/error-reporting writes and retries that observe no current data. Only the same successful completion UPDATE that evaluates the original deadline can clear it. New deletion starts pending. The remaining seven-day backend window then fits within thirty days of original deletion **if cleanup succeeds by that deadline**. Five-minute operation is the expected maintenance interval, not a substituted deadline or evidence of physical expiry. Failed purges retry and expose independent failure plus a failed scheduled invocation. A selective per-user status-reporting failure remains a global failure and cannot abort later trusted tombstone purges. Shared generic verification invalidation also acknowledges known deleted owners before erasing their only residual evidence; a selectively unacknowledged known row is protected without blocking other owners' credential purges. Too many protected IDs postpone that generic invalidation rather than exceed native parameter limits. Global expired-state cleanup follows tombstone processing and is skipped on failure. Crossing the deadline records an overdue retention incident even if a later purge succeeds; reopening is refused. A missing cron, provider outage, lost authority or failed deadline cannot be reported as compliant expiry. The operator must monitor actual trigger/health evidence and repair failed maintenance before the deadline; unresolved overdue incidents require manual escalation and remain unverified. No lease TTL, automatic open, silently cleared incident or global-key destruction supplies this guarantee.
The operator must separately verify the actual plan/backend/window, provider bookmark semantics and copy inventory. Manual exports, downloaded snapshots, staging databases, disk backups and email-provider records need their own original-deletion deadlines; they cannot be silently excluded or refreshed by restoration. Do not introduce payload exports as routine backups. The authority stores minimal denial metadata rather than deleted credential payloads. Actor durable storage contains opaque owner/alarm metadata only; executable preparations and cookies are never persisted. Never PITR-restore a deleted actor to recover credentials or permission. A synthetic-only actual D1/DO experiment, retained-key evidence and provider retention/configuration evidence are required before closing #83. Local fixtures prove application logic, not provider aging/purge.

## Consequences

An additional Free-compatible database and several gate reads/writes per operation must be included in #84 cost/CPU/load measurements. Recovery trades fresh proof and client consent for avoiding stale passwords and revoked capabilities. Global pending-auth invalidation can require an unaffected participant to restart an unfinished login or recovery transaction, while established access remains unaffected by another participant's ordinary deletion. Security tombstones persist beyond payload expiry for restore safety; they contain opaque identifiers only. Loss of independent authority or unresolved drain favors unavailability over resurrection. The [operator runbook](../hosted-account-deletion.md) defines executable steps and evidence boundaries.


## Provider evidence checkpoint (2026-10-19)

The [separate provider experiment](../hosted-restore-provider-validation.md) now records actual isolated native D1 and SQLite-object restoration, authenticated restored synthetic ciphertext, configured seven-day history, one successful quiet cron and public closed-gate denial. Actual scheduled purge before a projection marker, full binding reconciliation with matching completed audit, explicit reopen and fresh-proof denial checks subsequently passed. Disposable-resource and scoped copy closeout also passed; the measured nonempty purge used 14.579 ms CPU despite a successful outcome, above the nominal 10 ms Free allowance, so sustainable pilot feasibility remains #84. These observations do not change this decision, prove elapsed physical expiry or activate the full owner-bearing runtime. Synthetic application checks and actual provider observations remain distinct.
