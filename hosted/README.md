# Hosted portal work

This private package contains the local Worker feasibility slice for [issue #70](https://github.com/rudeayelo/aimharder-mcp/issues/70) and the invited password portal for [issue #71](https://github.com/rudeayelo/aimharder-mcp/issues/71), part of [the hosted specification](https://github.com/rudeayelo/aimharder-mcp/issues/69). The [Google sign-in and explicit linking slice](../docs/hosted-google.md) completes #72 with synthetic policy coverage, actual provider setup, owner-reported explicit linking/returning Google login and independently verified stable identity/profile plus both methods. It is not a deployed pilot or a complete portal. The current Workers plan is verified as Free; the user supplied an existing Resend token to replace native Email Sending without a plan change. The sending domain is verified and the dedicated Worker has Resend configured; all three mail flows have provider delivery evidence and owner-confirmed mailbox receipt, verified password login and recovery. Ticket #71 acceptance is complete using both synthetic policy tests and actual owner journeys. These functional checks do not establish CPU, load or operating cost.

From the repository root, install the local package with `pnpm install --frozen-lockfile`. Then, from this directory:

```sh
pnpm install --frozen-lockfile
pnpm typecheck
pnpm test
pnpm build
pnpm preview
```

CI runs the local and hosted checks separately. Root `pnpm test` covers the local package; this package's `pnpm test` runs the real workerd/D1 simulator and SDK v2 client. Both packages have separate lockfiles. The Google harness bundles `tests/portal-fixture-worker.ts` to a separate artifact and replaces only external Google token and Resend HTTP responses. The public npm package keeps SDK v1 and excludes `hosted/`.

The harness bundles separate fixture artifacts and provisions only synthetic identities, registered callbacks, email capture and external responses. The #74 harness exercises the actual production account boundary with D1 and SQLite Durable Objects, not a plaintext connection resolver. Every outbound request must match a synthetic boundary or the local authorization server. The build command bundles only `src/worker.ts`; it has no fixture provisioning/mail-inspection route or embedded credential/key. Missing vault bindings fail safely; an admitted account without a stored connection remains unconnected. No test credential or generated auth token belongs in a deployment configuration.

`AUTH_DB`, independent `RECOVERY_DB`, pinned `RECOVERY_AUTHORITY_ID`, `AUTH_SECRET`, and `BASE_URL` are required runtime bindings. Missing recovery authority/head fails closed; bootstrap it through the trusted [deletion/restore runbook](../docs/hosted-account-deletion.md). `AUTH_SECRET` belongs in platform secrets; the database binding must contain the maintained auth schema and admission migration. Enrollment, verification resend and recovery also require the `RESEND_API_KEY` platform secret and verified `MAIL_FROM`; without them they fail safely as unavailable. Ordinary tests do not contact the hosted domain or providers. The [isolated test setup](../docs/hosted-test-environment.md) uses pinned official Wrangler 4.151.1, `wrangler.test.example.jsonc` and a private resolved operator configuration outside the checkout; no operational IDs or active mail configuration belong in this template. `pnpm smoke:test-environment` is an explicit anonymous remote HTTP check. It defaults to the disabled-mail stage; set `HOSTED_SMOKE_MAIL_STAGE=configured` after enabling mail to omit all enrollment/recovery probes and keep the check free of mail side effects.

`migrations/0001-auth.sql` is generated by Better Auth 1.7.10's migration API against empty SQLite. `pnpm schema:generate` regenerates it for review; schema generation is not permission to apply a remote migration. Tests apply it only to disposable local D1. Future auth upgrades must review generated changes and migration/rollback behavior.

`migrations/0002-invitations.sql` stores application admission policy, distinct from the maintained auth schema. Apply both in order only in an authorized environment. `pnpm owner:prepare` creates private, offline owner-bootstrap artifacts outside the checkout and does not apply or send them. `pnpm preview` serves the production entry anonymously with disposable local state, no sender and external requests denied; use `PREVIEW_BASE_URL` with a Tailscale URL for a shared review. See [password portal setup, sender activation and acceptance](../docs/hosted-admission.md) for configuration, bootstrap, public routes and honest safe outcomes.

See [hosted feasibility evidence](../docs/hosted-feasibility.md) for dependency compatibility, metadata policy, hashing measurements, the conditional cost envelope, and the remaining acceptance stages.

Google access optionally requires both `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` platform secrets. Apply `migrations/0003-account-method-uniqueness.sql` after the two initial migrations before enabling it; existing duplicate provider subjects fail migration for review rather than being merged. The [Google runbook](../docs/hosted-google.md) covers exact callback setup, Testing policy, explicit same-account linking, fresh Google proof for password addition, public routes and the separate observed owner/operator acceptance evidence.

The [MCP authorization runbook](../docs/hosted-mcp-authorization.md) covers migration `0004-mcp-grants.sql` and trusted client registration. The [AimHarder connection runbook](../docs/hosted-aimharder-connection.md) adds migration `0005-aimharder-connection.sql`, the private `ACCOUNT_CONNECTIONS` SQLite object binding and separately held `VAULT_KEYS` / `VAULT_ACTIVE_KEY_ID` platform secrets. It documents initial browser connection, verified gym settings, encrypted credential custody and the trusted offline `pnpm vault:prepare-rotation` command. No replacement, lifecycle or sporting-write route is exposed by #74. Platform custody/deployment and live upstream access remain separate operator gates.

The [schedule/workout/booking guide](../docs/hosted-schedule-queries.md) and [personal activity/RM guide](../docs/hosted-activity-queries.md) cover the eight existing read tools now exposed beside account context on the protected HTTP endpoint. Each complete query runs through the verified subject's account object with its owned API client. Both roles retain these reads; no sporting-history replica or hosted sporting-write route is added by these query slices. Their SDK/workerd/D1/object tests synthesize only external HTTP; actual ChatGPT/Hermes and deployment acceptance remain separate.

The [participant administration guide](../docs/hosted-participants.md) covers minimal roles/status/configuration listing, suspension/reactivation and migration `0008-participant-access-generation.sql`. Suspension denies new portal/MCP use outside the actor queue, preserves encrypted configuration and requires fresh MCP consent after reactivation. Prepared actions bind the participant access generation; already possible sends retain original-account read-back without replay. This synthetic slice has no provider activation or actual client acceptance claim.

The [account deletion and controlled restore guide](../docs/hosted-account-deletion.md) adds application migration `0009`, the separate authority schema and `pnpm recovery:prepare`. Explicit owner deletion removes active service data and client access without changing AimHarder. Restore closes/drains nonexpiring leases, seals the latest opaque security manifest and preserves only matching connection revisions while requiring fresh auth/consent. Native provider retention/restore and cost/client acceptance are separate gates; local fixtures do not establish them.

Retention enforcement also requires the actual five-minute tombstone-only scheduled handler/trigger and independent cleanup health. It purges known deleted active data even under a closed gate or held original read, queues memory erasure afterward, never reopens and records a cleanup deadline 23 days after original deletion plus sticky overdue incident. Verify Free trigger capacity/CPU and provider invocations separately; missing/failed maintenance is not proven expiry.
