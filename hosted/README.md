# Hosted feasibility gate

This private package contains the local Worker feasibility slice for [issue #70](https://github.com/rudeayelo/aimharder-mcp/issues/70), part of [the hosted specification](https://github.com/rudeayelo/aimharder-mcp/issues/69). It is not a deployed pilot or a complete portal.

From the repository root, install the local package with `pnpm install --frozen-lockfile`. Then, from this directory:

```sh
pnpm install --frozen-lockfile
pnpm typecheck
pnpm test
pnpm build
```

CI runs the local and hosted checks separately. Root `pnpm test` covers the local package; this package's `pnpm test` runs the real workerd/D1 simulator and SDK v2 client. Both packages have separate lockfiles. The public npm package keeps SDK v1 and excludes `hosted/`.

The test harness bundles `tests/fixture-worker.ts` separately and provisions only synthetic identities, an exact registered callback, and a synthetic account resolver. Every outbound request must match the synthetic upstream or the local authorization server. The build command bundles only `src/worker.ts`; it has no fixture provisioning route, no account credentials, and no configured vault. Authenticated account queries therefore return a safe unconnected state until the later vault slice supplies `ResolveConnection`. No test credentials or generated auth tokens belong in a deployment configuration.

`AUTH_DB`, `AUTH_SECRET`, and `BASE_URL` are required runtime bindings. `AUTH_SECRET` belongs in platform secrets; the database binding must contain the maintained auth schema. The domain is not configured or contacted by these checks. There is deliberately no deployment command or provider configuration in this gate.

`migrations/0001-auth.sql` is generated by Better Auth 1.7.10's migration API against empty SQLite. `pnpm schema:generate` regenerates it for review; schema generation is not permission to apply a remote migration. Tests apply it only to disposable local D1. Future auth upgrades must review generated changes and migration/rollback behavior.

See [hosted feasibility evidence](../docs/hosted-feasibility.md) for dependency compatibility, metadata policy, hashing measurements, the conditional cost envelope, and the remaining acceptance stages.
